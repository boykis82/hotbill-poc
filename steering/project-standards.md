# 비즈니스
이 workflow는 유무선 통신 billing system의 hotbill 모듈의 설계서를 작성합니다. legacy system이 존재하고 이를 재구축하는 과정입니다.

## 비즈니스 정의
- bulk성으로 수행되는 정기청구 요금계산이 아닌, 실시간 요금계산을 hotbill이라 칭합니다.
- 단순 요금 조회성 hotbill, 해지정산을 위한 hotbill 등 수십가지의 hotbill usecase가 존재합니다.
- 유무선 통신 시스템이기 때문에 이동전화, 인터넷, IPTV 등 다양한 계약유형을 지원합니다.
- hotbill의 인입 경로는 모바일 앱, 백오피스 화면 등 다양합니다.
- 일부 hotbill usecase, 계약 유형은 대외 시스템 연동을 통해 과금 자료를 추가로 받아와야 하는 경우도 있습니다.
- tmforum spec을 따릅니다.

# 기술 정의
## 사용 언어, 기술, dbms
- Java 25
- Spring boot 4.x
- mybatis
- oracle

## 아키텍쳐
- api submodule과 impl submodule로 구성합니다.
- 정기청구, hotbill 모두 공통으로 사용하는 요금계산 api가 별도로 존재합니다. 이는 별도 모듈이므로 이 프로젝트에서는 stub으로 처리합니다.


# hotbill 프로세스 순서
1. 어딘가에서 hotbill 요청 rest api 인입. n개의 계약에 hotbill 처리할 수 있어야 함. hotbill 유스케이스에 따라 in/out이 다름
2. hotbill api 호출
3. 각 계약에 대해 hotbill 진행상태를 '요청중'으로 기록
4. 계약 유형 별로 다른 시스템으로 과금 자료를 요청해야 하는 경우가 있음. 분기하여 명시함.

## 다른 시스템의 과금 자료 필요 시
5. 다른 시스템에서 제공하는 rest api를 통해 과금 자료를 요청. 비동기로 이뤄지기 때문에 바로 return됨. 한번에 여러 계약에 대해 요청 가능
6. 종료

잠시 뒤, 다른 시스템에서 요금계산 결과를 담아서 hotbill module의 과금자료 등록 rest api를 호출함. api입력으로 ChargeData의 list를 받음
ChargeData에는 계약번호, list of (과금항목,청구금액) 가 들어가 있어야 함.

7. 요금계산 결과를 받으면 과긍자료 테이블에 저장. 동일 계약번호 존재 시 삭제 후 저장
8. 자료 전달받은 각 계약에 대해 hotbill 진행상태를 '요금계산 전'으로 기록. 자료에 오류코두가 들어 있으면 hotbill 진행상태를 '과금자료 오류'로 기록하고 return
9. 요금계산 api 호출. 이 api에서는 계산결과를 핫빌청구정보 테이블에 적재하고, 이 내역을 리턴함.
10. 요금계산이 성공한 계약에 대해 hotbill 진행상태를 '요금계산 완료'로 기록. 오류시 '실패'로 기록


## 다른 시스템의 과금 자료 불필요 시
5. 각 계약에 대해 hotbill 진행상태를 '요금계산 전'으로 기록
6. 요금계산 api 호출. 이 api에서는 계산결과를 핫빌청구정보 테이블에 적재하고, 이 내역을 리턴함.
7. 요금계산이 성공한 계약에 대해 hotbill 진행상태를 '요금계산 완료'로 기록. 오류시 '실패'로 기록
8. 요금계산 결과 return

# hotbill 결과조회 프로세스 순서
1. 인입된 계약번호 중 hotbill 진행상태가 '요금계산 완료'인게 하나라도 있으면 '요금계산 미완료' 오류 리턴
2. 인입된 계약번호의 핫빌청구정보 내역을 리턴


# 해지정산 프로세스 순서
1. 해지정산 완료 rest api 인입. n개의 계약에 hotbill 처리할 수 있어야 함. 이 중 hotbill 완료되지 않은 계약이 있으면 오류 리턴
2. 요금계산 api에서 posting대상을 테이블에 insert해준 내역 (이하 포스팅이력)을 읽어옴. 포스팅이력을 보고 업무 테이블에 update 처리 (주로 일시, 일자 컬럼). 그리고  
- 포스팅이력은 계약번호, hotbill일자, 일련번호까지 PK로 구성됨.
- 포스팅이력에는 [대상테이블, 테이블의 pk, list of (변경 대상 컬럼, 변경 대상 컬럼의 변경 후 값)]이 json 컬럼으로 들어가 있음
3. 핫빌취소로그에 변경 대상 데이터의 변경 전 snapshot 정보를 기록
4. 핫빌청구정보 테이블의 데이터를 청구정보 테이블로 이관. (핫빌청구정보는 임시성 데이터로 해지정산이 완료되면 추후 청구서,수납 처리를 위해 본 청구정보 테이블로 이관됨)
5. 핫빌청구정보 테이블의 해지정산여부 := Y 로 갱신
6. hotbill 진행상태롤 '해지정산 완료'로 기록

# 해지정산 당일 취소 프로세스 순서
1. 해지정산 당일 취소 rest api 인입. n개의 계약에 hotbill 처리할 수 있어야 함. 이 중 hotbill 해지정산 완료되지 않은 계약이 있으면 오류 리턴
2. 핫빌취소로그를 참조하여 업무 테이블 데이터 원복
3. 청구정보 테이블의 데이터 삭제
4. 핫빌청구정보 테이블의 해지정산여부 := N 로 갱신
5. hotbill 진행상태롤 '요금계산 완료'로 기록


# 요구사항
1. 다양한 hotbill usecase가 존재합니다. usecase가 추가되어도 기존 로직에는 영향을 주면 안됩니다. 핫빌 유스케이스 별로 로직이 크게 달라지진 않습니다. 일부 특화 로직이 들어가는 경우가 있기 때문에 template method pattern이 더 적합할 수도 있습니다. validation 부분만 확장 가능하게 설계하세요.
- 단순 요금 조회
- 해지 요금 조회
- 번호이동 portout
- 직권해지를 위한 요금 조회

2. 계약 유형에 따라 다른 시스템들로부터 과금 자료를 요청해야 하는 경우, 그렇지 않은 경우가 존재합니다.
과금 자료 연동이 불필요하면 hotbill 요청시 sync 방식으로 처리되고, 과금 자료 연동이 필요하면 async 방식으로 처리됩니다.
- 이동전화 : 전화과금자료 시스템 연동 필요
- IPTV : 컨텐츠과금자료 시스템 연동 필요
- 인터넷 : 연동 불필요
역시 OCP를 준수합니다. 과금 자료 연동이 필요한 계약 유형이어도 hotbill usecase에 따라 연동하면 안되는 경우도 고려해 주세요.

3. Hotbill interface, HotbillImpl class를 만들고, 아래와 같이 총 4개의 api를 제공한다.
- hotbill 요청
- hotbill 결과조회
- 해지정산 요청
- 해지정산 당일취소

4. rest api endpoint는 아래와 같이 구성한다.
- 해지요금 요청
- 해지요금 결과조회
- 실시간요금 요청
- 실시간요금 결과조회
- 해지정산 요청
- 해지정산 당일취소
- 과금자료 등록 (다른 과금 시스템에서 호출)

5. 핫빌취소로그에는 여러 테이블에 대한 내역이 담길 수 있습니다. 이를 유연하게 처리할 수 있도록 설계하세요.
프로젝트 보안 정책 상 mybatis에 dynamic sql을 넣을 수 없습니다. 그래서 posting 대상 테이블 별로 실행하야 할 update mapper를 유연하게 관리해야 합니다. 또는 다른 좋은 방법이 있다면 제안도 가능합니다.

6. 여러 개의 계약번호를 한번의 입력으로 받아서 hotbill 처리가 가능해야 합니다. 이들의 계약 유형은 서로 다를 수 있습니다. 한번에 인입되는 경우, hotbill usecase는 모두 동일합니다.
