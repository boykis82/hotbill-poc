# Hotbill 모듈 요구사항 명세서

## 1. 개요

### 1.1 프로젝트 목적
- 유무선 통신 billing system의 실시간 요금계산(hotbill) 모듈 재구축
- Legacy 시스템을 Java 25, Spring Boot 4.x 기반으로 현대화
- TMForum 스펙을 준수하는 확장 가능한 아키텍처 구현

### 1.2 비즈니스 정의
- **Hotbill**: bulk성 정기청구 요금계산이 아닌 실시간 요금계산
- **지원 계약 유형**: 이동전화, 인터넷, IPTV
- **인입 경로**: 모바일 앱, 백오피스 화면 등
- **외부 연동**: 일부 usecase와 계약 유형은 대외 시스템 연동 필요

## 2. 기능 요구사항

### 2.1 Hotbill API 제공 (4개 API)
1. **Hotbill 요청**: 실시간 요금계산 요청 처리
2. **Hotbill 결과조회**: 요금계산 결과 조회
3. **해지정산 요청**: 해지정산 완료 처리
4. **해지정산 당일취소**: 해지정산 취소 처리

### 2.2 REST API Endpoint (7개)
1. 해지요금 요청
2. 해지요금 결과조회
3. 실시간요금 요청
4. 실시간요금 결과조회
5. 해지정산 요청
6. 해지정산 당일취소
7. 과금자료 등록 (외부 과금 시스템에서 호출)

### 2.3 Hotbill Usecase 지원
다음 usecase들을 지원하며, 신규 usecase 추가 시 기존 로직에 영향 없이 확장 가능해야 함:
- 단순 요금 조회
- 해지 요금 조회
- 번호이동 portout
- 직권해지를 위한 요금 조회

**확장성 요구사항**:
- Template Method Pattern 적용 고려
- Validation 부분만 확장 가능하게 설계
- OCP(Open-Closed Principle) 준수

### 2.4 계약 유형별 과금자료 연동
계약 유형에 따라 외부 시스템 연동 여부가 결정됨:

| 계약 유형 | 연동 시스템 | 처리 방식 |
|---------|-----------|---------|
| 이동전화 | 전화과금자료 시스템 | 비동기(Async) |
| IPTV | 컨텐츠과금자료 시스템 | 비동기(Async) |
| 인터넷 | 연동 불필요 | 동기(Sync) |

**확장성 요구사항**:
- 과금자료 연동 필요 계약 유형이어도 hotbill usecase에 따라 연동 생략 가능
- OCP(Open-Closed Principle) 준수

### 2.5 다중 계약 일괄 처리
- 한 번의 요청으로 N개의 계약 처리 가능
- 각 계약의 계약 유형은 서로 다를 수 있음
- 한번에 인입되는 계약들의 hotbill usecase는 동일함

## 3. 프로세스 요구사항

### 3.1 Hotbill 요청 프로세스

#### 3.1.1 공통 처리
1. REST API로 hotbill 요청 인입 (N개 계약)
2. Hotbill API 호출
3. 각 계약의 hotbill 진행상태를 '요청중'으로 기록
4. 계약 유형별로 과금자료 연동 필요 여부 판단

#### 3.1.2 과금자료 연동 필요 시 (비동기)
5. 외부 시스템 REST API로 과금자료 요청 (비동기, 즉시 return)
   - 한번에 여러 계약 요청 가능
6. 프로세스 종료

**[비동기 콜백]** 외부 시스템에서 과금자료 등록 API 호출:
- 입력: `List<ChargeData>`
- ChargeData 구성: 계약번호, List<(과금항목, 청구금액)>

7. 과금자료를 과금자료 테이블에 저장
   - 동일 계약번호 존재 시 삭제 후 저장
8. 각 계약의 hotbill 진행상태 갱신:
   - 정상: '요금계산 전'
   - 오류코드 존재: '과금자료 오류' (처리 종료)
9. 요금계산 API 호출
   - 계산결과를 핫빌청구정보 테이블에 적재
   - 계산결과 return
10. hotbill 진행상태 갱신:
    - 성공: '요금계산 완료'
    - 실패: '실패'

#### 3.1.3 과금자료 연동 불필요 시 (동기)
5. 각 계약의 hotbill 진행상태를 '요금계산 전'으로 기록
6. 요금계산 API 호출
   - 계산결과를 핫빌청구정보 테이블에 적재
   - 계산결과 return
7. hotbill 진행상태 갱신:
   - 성공: '요금계산 완료'
   - 실패: '실패'
8. 요금계산 결과 return

### 3.2 Hotbill 결과조회 프로세스
1. 인입된 계약번호 중 hotbill 진행상태가 '요금계산 완료'가 아닌 것이 하나라도 있으면 '요금계산 미완료' 오류 return
2. 인입된 계약번호의 핫빌청구정보 내역 return

### 3.3 해지정산 요청 프로세스
1. 해지정산 완료 REST API 인입 (N개 계약)
   - hotbill 완료되지 않은 계약이 있으면 오류 return
2. 포스팅이력 조회 및 업무 테이블 갱신
   - **포스팅이력 PK**: 계약번호, hotbill일자, 일련번호
   - **포스팅이력 JSON 컬럼**: [대상테이블, 테이블의 PK, List<(변경대상컬럼, 변경후값)>]
   - 업무 테이블 UPDATE 처리 (주로 일시, 일자 컬럼)
3. 핫빌취소로그에 변경 전 snapshot 정보 기록
4. 핫빌청구정보 → 청구정보 테이블로 데이터 이관
5. 핫빌청구정보 테이블의 해지정산여부 = 'Y'로 갱신
6. hotbill 진행상태를 '해지정산 완료'로 기록

### 3.4 해지정산 당일취소 프로세스
1. 해지정산 당일취소 REST API 인입 (N개 계약)
   - 해지정산 완료되지 않은 계약이 있으면 오류 return
2. 핫빌취소로그를 참조하여 업무 테이블 데이터 원복
3. 청구정보 테이블의 데이터 삭제
4. 핫빌청구정보 테이블의 해지정산여부 = 'N'로 갱신
5. hotbill 진행상태를 '요금계산 완료'로 기록

## 4. 비기능 요구사항

### 4.1 확장성 (OCP 준수)
- **Hotbill Usecase 확장**: 신규 usecase 추가 시 기존 로직 변경 없음
- **계약 유형 확장**: 신규 계약 유형 추가 시 기존 로직 변경 없음
- **과금자료 연동 정책 확장**: usecase와 계약 유형 조합에 따른 연동 정책 유연하게 관리

### 4.2 유연한 데이터 처리
- **핫빌취소로그**: 여러 테이블에 대한 내역을 유연하게 처리
- **Dynamic SQL 제약**: MyBatis에 dynamic SQL 사용 불가
- **해결 방안**: 포스팅 대상 테이블별 UPDATE mapper 유연하게 관리

### 4.3 모듈 구조
- **api submodule**: 인터페이스 정의
- **impl submodule**: 구현체
- **요금계산 API**: 별도 모듈 (stub으로 처리)

### 4.4 준수 사항
- TMForum 스펙 준수
- Template Method Pattern 적용 (usecase별 특화 로직 처리)
- Strategy Pattern 적용 고려 (계약 유형별 과금자료 연동 정책)

## 5. 기술 스택

- Java 25

- MyBatis

### 5.2 데이터베이스
- Oracle

## 6. 데이터 모델 요구사항

### 6.1 핵심 테이블
1. **Hotbill 진행상태 테이블**
   - 진행상태: 요청중, 요금계산 전, 과금자료 오류, 요금계산 완료, 실패, 해지정산 완료

2. **과금자료 테이블**
   - 외부 시스템에서 전달받은 과금자료 저장
   - 계약번호 중복 시 삭제 후 재저장

3. **핫빌청구정보 테이블**
   - 임시 청구정보 저장
   - 해지정산여부 컬럼 포함

4. **청구정보 테이블**
   - 본 청구정보 (청구서, 수납 처리용)

5. **포스팅이력 테이블**
   - PK: 계약번호, hotbill일자, 일련번호
   - JSON 컬럼: 대상테이블, 테이블 PK, 변경컬럼 정보

6. **핫빌취소로그 테이블**
   - 변경 전 snapshot 저장
   - 여러 테이블에 대한 내역 저장 가능

## 7. 외부 인터페이스 요구사항

### 7.1 외부 시스템 호출 (Outbound)

- 컨텐츠과금자료 시스템 REST API

### 7.2 외부 시스템에서 호출 (Inbound)

### 7.3 내부 모듈 호출
- 요금계산 API (stub으로 처리)

## 8. 제약사항

### 8.1 보안 정책
- MyBatis에 dynamic SQL 사용 불가
- 대안: 테이블별 mapper 관리 또는 다른 방법 제안 필요

### 8.2 레거시 연동
- Legacy 시스템 재구축 프로젝트
